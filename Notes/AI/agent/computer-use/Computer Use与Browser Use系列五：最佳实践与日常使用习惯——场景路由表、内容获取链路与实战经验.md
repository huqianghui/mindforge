## 引言：这套能力对我意味着什么

我的日常工作流以**知识查询、内容获取、沉淀个人知识库（PKC）**为主——恰好是读取密集型场景，也恰好是 Computer Use / Browser Use 解决得最彻底的一类。

在 Codex 原生浏览器能力出现之前，最痛的一环一直是**认证网站的内容获取**：Claude Code 的 WebFetch/tavily 对需要登录的站点永远返回空内容或登录页（根本原因：无状态的服务端抓取，没有我的浏览器会话），最后被迫立了硬规则——认证站点直接用 Playwright 脚本，还要处理 ChatGPT share 页 DOM 虚拟化这类深坑。

Codex 的 Chrome extension 模式从根上改变了这件事：**Agent 不再"从外面抓"，而是"坐进我已登录的浏览器里看"**。登录态、JS 渲染、搜索引擎结果页，一次性全部解决。本篇记录我围绕这套能力形成的使用习惯。

## 一、我的场景路由表

前四篇给的是通用决策逻辑，这里是我实际使用的默认路由——遇到任务先查这张表：

| 我的高频场景 | 用什么 | 为什么 |
|---|---|---|
| 知识查询、公开资料检索 | 内置浏览器（`@Browser`） | 不需要登录态；可以直接开 Google/Bing 搜索并读结果页，不受搜索 API 配额和覆盖面限制 |
| 需要登录的内容获取（GitHub、订阅站、企业系统） | `@Chrome` 外部接管（画中画） | 复用真实 Chrome 的登录态，不用重新认证 |
| 边读网页边提问、就地整理 | Side chat（扩展侧栏） | 页面/选中文本直接进上下文，聊天同步回桌面应用 |
| 前端开发修 UI | Browser comments（内置浏览器批注） | 批注锚定渲染后的元素，省掉"截图+文字描述位置"的损耗 |
| 反爬严格的站点（如 mp.weixin.qq.com 类） | **放弃自动化，手动复制** | 见"放弃标准"一节 |
| 视频内容 | 字幕导出（`exportYouTubeTranscript` 类能力） | 拿文本再消化，比"让 Agent 看视频"现实得多 |

浏览器覆盖上，官方扩展支持 Chrome/Edge/Brave/Opera/Vivaldi——我常用的 Chrome 和 Edge 都在列，日常已经够用。headless/CI 场景这套能力不可用，但那本来就不是它的主场。

## 二、权限配置：我选择最大放行

我把权限配置为**最大权限、全部放行**。理由和实际体验：

- 我的场景以读为主，写操作（发送、提交、删除）本来就少
- 逐次确认对读取密集型工作流是纯摩擦——每读一个页面点一次头，效率损失远大于风险收益
- 放行后大部分读取任务可以一气呵成，体验接近"说一句话拿到结果"

但要知道**权限开关关不掉的东西**（系列二的四级策略中 Level 1 是产品硬编码）：

- CAPTCHA——每次都会停下来问我是否要它解
- 付费墙、HTTPS 安全警告——明确禁止绕过，只能人接管
- 修改密码的最终提交——必须亲手做

实践感受：这些硬拦截触发频率很低（我对反爬站点本来就选择手动），所以"最大放行 + 偶尔接管"是读取型工作流的最优配置。**如果你的场景涉及大量写操作（发消息、提交表单），不建议照抄这个配置**——那种场景下确认摩擦是保护，不是负担。

## 三、放弃标准：知道什么时候不用工具

不是所有站点都值得自动化。我的放弃标准：

1. **反爬严格的站点**——即使带着真实浏览器指纹和登录态，频繁自动化访问仍可能触发风控。extension 模式让 Agent 和普通用户难以区分，但不是风控豁免。这类站点我直接手动复制内容，几十秒的事，不值得赌账号风险
2. **DOM 虚拟化的长列表页**——只渲染视口附近内容，Agent 滚动抓取必然缺失（ChatGPT share 页的教训）。要么找该站点的导出/API 通道，要么手动
3. **一次性的小内容**——手动复制比描述任务给 Agent 更快的，就手动

判断原则一句话：**自动化的价值 = 重复次数 × 单次节省 − 失败风险**。一次性任务和高风险站点，这个式子通常算不过来。

## 四、内容完整性核验：从 ChatGPT share 迁移过来的铁律

这可能是本篇含金量最高的一条，因为官方文档完全不提。

我在 ChatGPT share 页抓取上吃过亏：DOM 虚拟化导致滚动抓取严重缺内容，差点基于不完整素材写文章。由此立下的规矩**直接迁移**到所有 browser use 任务：

> **抓取后必须核验完整性，不完整先报告、绝不动笔。**

具体核验动作：

- **数量核验**：消息数/条目数/章节数与预期一致（页面上通常有总数提示）
- **关键词核验**：我记得内容里出现过的关键词，grep 得到
- **悬置核验**：没有"提了问题没有回答"这类断裂
- **边界核验**：开头和结尾都在（长页面懒加载最容易丢尾部）

browser use 时代这条规矩不是过时了，而是更重要了——Agent 读长页面、导出字幕、整理多页内容时，**虚拟化列表和懒加载照样会让它拿到残缺内容，而 Agent 自己通常意识不到缺了**。它会基于拿到的部分自信地总结。核验责任在我，不在它。

为什么换了工具问题还在？因为**虚拟化是页面本身的性质，不是抓取工具的缺陷**。ChatGPT share 页不管谁来看——肉眼、Playwright、browser use、extension——浏览器渲染出的活 DOM 里都只有视口附近的几条消息；browser use 的 `domSnapshot()` 读的正是这个活 DOM，拿到的和手写 Playwright 一样残缺。当年真正的解法也不是换渲染工具，而是**换数据层**：从整页 HTML 里提取 turbo-stream 数据块直接解析——数据层天然是全的，UI 层天然是虚拟化的。browser use 带来的真实改进是让"拿数据层"变容易了（`evaluate()` 可直接在页面跑 JS 读应用状态、`content.export()` 和字幕导出走的就是数据通道），但 Agent 的**默认读取路径仍是 DOM snapshot**——所以它解决的是登录态和 JS 渲染，不解决"虚拟化只渲染视口"，核验规矩继续留着。

另一条相关经验：**分享链接是创建时刻的快照**（ChatGPT share 的教训）——对话后来追加的内容不会同步进旧链接。让 Agent 读任何"分享页"之前，先确认链接是最新的。

## 五、获取 → 知识库：Codex 当前端，Claude Code 当后端

这是我工作流里最重要的分工设计。我的 PKC（Personal Knowledge Compiler）管线是：

```
① 内容获取          ② 成文落盘           ③ 知识编译              ④ 检索
认证页面/JS渲染   →  vault 笔记 +       →  wiki 提取（Claims/    →  qmd 混合索引
登录态/搜索          README 导航            概念页/关联）
```

过去最痛的是第①环，现在的分工：

- **Codex（获取前端）**：负责"把内容拿回来"——读登录页面、导出字幕、搜索汇总。它的原生浏览器能力在这一环无可替代
- **Claude Code（编译后端）**：负责"把内容知识化"——vault 规则、agent 路由、wiki schema、loop engineering 全部沉淀在这边。这些是多年积累的 harness 资产，不随获取工具切换

两点实践注意：

1. **交接格式要约定**：Codex 落盘的内容按 vault 笔记规范来（frontmatter 的 title/created/tags、中文正文英文术语、外链用内容标题做链接文本），否则编译环节要先做一轮格式清洗
2. **不是二选一**：这是按环节各用所长，也是 agent fan-out（同一任务多 agent 横评）思路的自然延伸——不同 harness 有不同的原生能力禀赋，路由到擅长的环节

> 🔄 **待回填**：走通几次"Codex 获取 → vault 落盘 → /extract-knowledge → qmd embed"完整链路后，把衔接处的摩擦点（格式、路径、遗漏）记录到这里。

## 六、Browser comments：前端开发的反馈闭环（准备实践）

我准备在网页开发中用 comments 模式做前端修改的主要反馈通道。基于系列一的调研，先立三条使用规矩：

**① 批注用三段式**——现象 + 期望 + 负向约束：

```text
移动端 390px 宽度下，这个按钮文字溢出。
优先保持单行；无法保持时才换行。
不要改变卡片高度，也不要修改桌面端布局。
```

第三行最容易忽略、最重要——不写负向约束，Agent 可能顺手重排整个布局，修一个 bug 引出三个。

**② 状态类 bug 补上下文**——批注只锚定视觉位置，不锚定触发条件。hover 才出现、特定数据才触发的问题，批注里写明 viewport、复现步骤、当前页面状态。

**③ 先 Adjust 再发送**——Annotation mode 的 Adjust 能先在界面上把字体/间距/颜色调到满意，再把明确参数发给 Agent，把"调到什么程度"从文字描述变成所见即所得。

已知边界：comments 跑在内置浏览器（独立 Profile），本地 dev server 是主场景；需要登录态才能到达的页面状态，要么内置浏览器里登一次，要么 dev 环境提供免登录 mock。

> 🔄 **待回填**：实际用过一轮后记录——"批注 → 修改 → 验证"一个来回的真实耗时；它在哪类 bug 上失手（预期：跨组件的状态逻辑类）；与 Playwright spec 截图流程（我在项目里已有的做法）如何配合分工。

## 七、隐私边界：真实 Chrome 意味着什么

用 `@Chrome` 接管真实浏览器，等于 Agent 能看到**所有**已登录站点。我的边界设定：

1. **页面内容会进模型上下文**——这是使用前提，不是 bug。让 Agent 读哪个页面，等于把该页面内容发给模型服务（我的场景下是 Azure OpenAI endpoint）
2. **个人敏感页面不指给 Agent**——个人邮箱、账户设置、支付页面，没有让 Agent 读的理由
3. **接管有明确的开始和结束**——任务结束后未标记的标签页会释放控制；不留"常驻控制"
4. **知识库有自己的隐私分层**——获取回来的内容落盘时同样遵守 vault 的私有/公开边界（私人内容永远不进 git），获取工具的改变不改变落盘纪律

原则一句话：**登录态是我借给 Agent 的，按任务借、任务完收回，不是常驻授权。**

## 八、失败模式与恢复习惯

按遇到频率排列的处理习惯：

| 失败模式 | 我的处理 |
|---|---|
| 页面卡在 Cookie 弹窗/通知请求上 | 让它继续（Cookie 同意是免确认类）；卡住超过一轮就我手动点掉 |
| tab 失效/被我误关 | 让 Agent 从同一 browser 重开 tab 即可——binding 不失效（系列二的协议），不需要重来 |
| 读取结果明显不完整 | 触发第四节的核验流程；懒加载页让它先滚到底再读；仍缺就换导出通道或手动 |
| Agent 在某个交互上反复重试 | 直接接管——判断标准很简单：**我看它试第二次失败，就自己上**。等待第三次重试的时间总是浪费的 |
| 浏览器控制被扩展/我打断 | 正常现象，重新发起即可，binding 还在 |

通用心法：**browser use 的正确预期是"半自动"而非"全自动"**——它把 90% 的机械操作接走，剩下 10% 的关键节点（登录、验证码、模糊判断）本来就该是人的。带着这个预期用，体验是解放；带着"全自动"预期用，体验是失望。

## 九、可复现沉淀：把一次性对话变成资产

高频操作值得固化成 prompt 模板，而不是每次现场描述。我正在沉淀的几个：

**内容获取落盘**：

```text
用 @Chrome 打开 <URL>，读取全文（懒加载页先滚动到底），
核验完整性（开头结尾都在、总数与页面提示一致），
然后按我 vault 的笔记格式落盘到 <目录>：
frontmatter 含 title/created/tags，中文正文、英文术语，
外链用内容标题做链接文本。不完整就先报告，不要落盘。
```

**搜索汇总**：

```text
用内置浏览器搜索 <主题>，打开前 N 个最相关结果，
每个来源给出：核心观点、与我已有认知的差异点、原文链接。
只要一手来源，跳过内容农场。
```

**视频转笔记**：

```text
打开 <视频URL>，导出字幕，
按"核心论点 → 论据 → 我可以行动的点"三段整理，
标注时间戳方便回看。没有字幕就直接告诉我，不要猜内容。
```

这些模板的共同点：**把核验要求和落盘格式写进指令本身**，让每次执行自带质量门禁——这与 SkillOpt 的思路一致，prompt 即资产，用数据迭代它。

> 🔄 **待回填**：模板实际使用后的迭代版本；是否值得升级为 Codex 侧的自定义 skill/plugin。

## 小结：我的五条使用守则

1. **按表路由**——登录态找 @Chrome，公开检索用内置浏览器，边读边问开 side chat，修 UI 用 comments
2. **读取型场景最大放行，硬拦截欣然接管**——确认摩擦和场景风险要匹配，不盲从默认也不盲从"全放行"
3. **核验永远在我**——数量、关键词、悬置、边界四查；Agent 不知道自己拿到的是残缺内容
4. **分工不站队**——Codex 管获取，Claude Code 管编译，按环节用所长
5. **登录态按任务借，模板即资产**——隐私边界靠习惯维持，高频操作固化成带质量门禁的 prompt
