# FinOps 系列 03：落地提纲——从使用洞见到优化、监控、评估闭环（活文档）

> 本篇是提纲而非定稿。[系列 01](FinOps系列01：从token价格到任务完成花费——指标转向与AI使用边界.md) 给出任务完成花费的公式与两栏边界，[系列 02](FinOps系列02：数据飞轮与RSI——三层嵌套循环与一个贯穿指标.md) 给出三层循环，本篇回答"从现有平台数据出发，第一步做什么"。标注 **待核实** 的条目表示尚未对照官方文档或实测验证，只记录方向；核实后改写为结论并在文末更新记录里登记。

---

## 一、目标与边界

目标是让组织能按任务算 AI 的账，而不是按 token 算。边界是：只讨论使用方（企业 AI 平台团队、FinOps 团队）能拿到的数据和能做的闭环，不讨论供给方的定价策略。

对应系列 02 的三层循环，本篇只覆盖中圈：使用洞见与遥测 → 评估 → 优化 → 部署。内圈 RSI 的落地留待有实测后单独成文。

## 二、数据源盘点：三类使用洞见能给什么、缺什么

用系列 01 的公式做对照：任务完成花费 = 模型调用成本 + 人工验证成本 + (1 − 成功率) × 错误成本。

| 数据源 | 能直接给出的 | 对应公式项 | 缺的 | 待核实 |
|---|---|---|---|---|
| GitHub Copilot usage / agent usage insights | 活跃用户、建议与接受次数、按语言与编辑器的分布、agent 会话与任务量 | 第一项的用量侧；接受率可作左栏任务成功率的代理 | 任务级"是否真正完成"（接受不等于可用）、后续人工修改耗时 | 接受率的定义粒度；agent 模式下是否暴露每任务的 token 与工具调用明细 |
| Copilot Studio analytics | 会话量、话题命中、升级到人工的比例、满意度 | 第一项用量侧；"升级到人工"是右栏任务验证成本的直接信号 | 每次会话的模型成本明细、错误成本（错误应答造成的下游损失） | 升级原因是否可导出分类；是否有按 topic 的成本视图 |
| AI Foundry 模型使用与可观测性 | 按模型/部署的 token 用量与费用、延迟、评估结果（若配置了评估） | 第一项完整；评估结果若有则对应成功率 | 业务任务与调用之间的映射（一个任务对应哪几次调用）、人工验证耗时 | 评估功能能否按任务分桶输出；trace 中是否能携带业务任务 ID |

三类数据源的共性：第一项齐全，第二项与第三项几乎为零。这印证系列 01 的判断，使用洞见告诉你用量在哪，不告诉你价值在哪。补齐后两项是落地的核心工作。

## 三、任务级度量的最小字段集

每条任务记录至少包含：

| 字段 | 来源 | 说明 |
|---|---|---|
| task_id | 业务系统或 harness | 把多次模型调用聚合到一个任务的键；trace 需携带此 ID |
| scenario_bucket | 人工标定一次，之后按规则映射 | 在两变量坐标（验证成本 × 错误成本）中的位置，至少分左栏/右栏两桶，建议四象限 |
| model_cost | 平台账单或 trace | 第一项。含 token、工具调用、检索、外部 API |
| success | 接收方判定 | 二值或分级。判定者不能是生成方（生成-评估分离） |
| verify_minutes | 接收方记录或系统推断 | 第二项。人从拿到输出到决定可用/不可用的耗时 |
| error_cost_est | 场景桶级别预设，任务级可覆写 | 第三项的单价。可逆任务给低值，不可逆任务按业务损失估 |
| reversible | 场景桶级别预设 | 是否可回滚，决定 error_cost_est 的量级 |

有了这七个字段，就能按桶算出任务完成花费的三项分解，判断每个桶离阈值曲线有多远，以及该用 token 层手段还是成功率手段。

**待核实**：三类平台的 trace 或 log 中，哪些能原生携带自定义 task_id 与 scenario_bucket，哪些需要在 harness 层自行注入。

## 四、工程闭环：优化、监控、评估各在什么位置

对应中圈的四个节点，三个工程环节的位置如下：

- **监控** 位于"使用洞见 / 遥测"节点。除了平台自带的用量面板，需要把第三节的字段接入，使监控对象从调用变成任务。监控的输出是分桶后的任务完成花费及其三项分解。
- **评估** 位于"评估"节点。左栏任务以 LLM-as-a-Judge 加抽样人工校准为主（RLHF 式主观分）；右栏任务优先接客观信号（测试结果、对账结果、审核结论，RLVR 式验证器），并为每个右栏桶明确回答"写得出验证器吗、信号延迟多久"，答不出的桶暂不进入优化阶梯 L2。评估器与被评估的生成方分离，评估集独立于优化用的数据。两本账分家：验收分不动，优化 reward 单设。
- **优化** 位于"优化"节点。左栏桶用 token 层手段（上下文裁剪、模型路由、输出压缩，见 [Agentic Engineering](../AI/Agentic-Engineering——质量与成本的一体化优化.md)）；右栏桶按 [成熟度阶梯](../AI/agent-lightning/Prompt优化成熟度阶梯——从vibe%20check、LLM-judge到数据闭环：APO与SkillOpt前置篇.md) 逐级上行：先规范 prompt，评估集到 30~50 条后引入 APO 或 [SkillOpt](../../wiki/concepts/skillopt.md)，有稳定客观 reward 后再考虑 SFT 与 RL。

Azure 博客 [Ship agents faster with expanded model choice, voice agents, and continuous optimization](https://azure.microsoft.com/en-us/blog/ship-agents-faster-with-expanded-model-choice-voice-agents-and-continuous-optimization/) 把这一圈称为 continuous optimization。**待核实**：该博客所述的平台能力具体覆盖上述哪些节点，评估与优化是否共用同一份数据（若共用，需要在使用时手动分家）。

## 五、推进顺序

1. 选一个右栏场景和一个左栏场景各一桶，先把第三节的七个字段跑通，哪怕人工填。
2. 用两桶的数据各算一次任务完成花费的三项分解，验证系列 01 的判断（左栏第一项主导、右栏第三项主导）是否在真实数据上成立。
3. 右栏桶开始积累人工验证样本，作为评估集种子；左栏桶直接上 token 层手段。
4. 右栏桶评估集到位后接 APO 或 SkillOpt，观察成功率曲线，估算距离阈值的差距。
5. 以上任一步产出结论，回写本篇对应小节，并考虑是否触发系列 02 待深入清单的更新。

## 六、开放问题

- 验证耗时（verify_minutes）在多数场景没有自动记录手段，靠人填的数据可持续性差。是否可以用"输出被修改的比例"或"从生成到提交的间隔"做代理。
- 错误成本估计在右栏任务里往往是尾部分布，少数事故占大部分损失。按期望值算会低估风险，是否需要在公式中引入分位数或风险溢价。
- 三类平台的数据导出粒度与频率不同，任务级聚合的时间对齐怎么做。
- 内圈 RSI 在这些场景里的第一个可行落点是什么，需要等右栏桶的评估集稳定后再判断。
- 供给方定价是否从 token 计费走向按任务或按结果计费（GitHub Copilot 的 premium request、agent 任务计量，Copilot Studio 与 AI Foundry 的 agent 计费单位）。**待核实**。若成立，系列 01 第六节的"Super App 阶段账单即任务完成花费"就从推论变为事实，度量口径可直接对齐账单。
- 模型侧的置信度校准能否把右栏桶的人工验证从"复核 100%"降到"复核被标记部分加抽检"：主流 LLM 的置信度输出是否可用、TypeSafe Jev 这类返回概率与置信度的决策模型在真实右栏任务上的校准质量。**待核实**。若成立，verify_minutes 字段应按"被标记 / 未标记"分开记录。
- 组织内各场景当前处于 Copilot / Cowork / Super App 哪个阶段，能否用第三节的字段自动判定（验证粒度是 token 级、task 级还是 outcome 级），从而给出每个场景的下一步是压 token 还是提成功率。
