# Viseme（视觉音素）

## 摘要

Viseme（vis- = see）是**眼睛看到的最小口型单位**，与 phoneme（音素，耳朵听到的最小语音单位）构成 `-eme` 词族（还有 grapheme 字素、morpheme 语素——各领域的最小功能单位）。关键关系：**多个 phoneme 映射到同一个 viseme**——/p/ /b/ /m/ 听起来不同但口型都是"双唇闭合→打开"；人眼能区分的口型数量远少于人耳能区分的音素数量，Azure 为 en-US 定义了 22 个 viseme ID（0–21）。

viseme 是语音驱动动画领域的基础单位，跨 TTS、数字人、3D 动画三个子域：TTS 引擎在合成音频的同时输出 viseme 时间轴（Voice Live 事件 `response.animation_viseme.delta`：`viseme_id` + `audio_offset_ms`），下游渲染层（云端神经渲染或客户端 blendshape/骨骼动画）按时间轴驱动口型。

## Claims

### Claim: viseme 序列比音素序列更接近渲染层——这是口型输出协议选 viseme 时间轴而非音素序列的原因

- **来源**：[[Voice-Live系列05：两类数字人头像]]
- **首次出现**：2026-09-23
- **最近更新**：2026-09-25
- **置信度**：0.8
- **状态**：active

> 几十个英语音素收敛到 22 个口型单位，渲染层只需关心视觉可区分的形状。官方文档 + 生产接入双重印证。

### Claim: viseme 是离散的驱动信号，渲染输出是连续的——"查表贴图"是误解，实际是协同发音条件下的神经渲染

- **来源**：[[Voice-Live系列05：两类数字人头像]]
- **首次出现**：2026-09-23
- **最近更新**：2026-09-25
- **置信度**：0.75
- **状态**：active

> 若按 viseme ID 查表贴预录口型帧，口型会像早期游戏 NPC 一样机械——真实说话中相邻音素口型互相渗透（协同发音 coarticulation：/s/ 接 /u/ 和接 /i/ 嘴形不同）。实际做法：深度视觉模型以音频/viseme 时间轴为条件逐帧合成嘴部及周边区域，再无缝融合回实拍素材。Video 头像的"素材回放"部分是身体、衣着、姿态；嘴是每次实时生成的（显式流水线 `audio → phoneme → viseme → mouth animation → 与素材合成`）。

### Claim: "viseme 是数字人准入闸门"约束的是"谁来出声"，不约束"头怎么动"

- **来源**：[[Voice-Live系列05：两类数字人头像]]、[[Voice-Live系列04：GPT-Live-1对数字人方案的影响]]
- **首次出现**：2026-09-23
- **最近更新**：2026-09-25
- **置信度**：0.75
- **状态**：active

> 闸门的准确含义：驱动信号必须来自 TTS 合成环节，所以数字人必然落在混合式/级联式路线——对两类头像都成立（photo 头像同样吃 Azure TTS 输出）。但 video 头像消费"音频 + viseme 时间轴"，photo 头像消费"音频波形本身"（VASA-1 直接从音频提特征，中间**没有显式 viseme 表示**，面部动力学作为联合潜变量整体建模）。此条精确化了 VL04 的初版表述。

### Claim: viseme 时间轴是云端计算与本地渲染两个位面的耦合接口，客户端自渲染要守六条同步规则

- **来源**：[[Blender系列04：人物面试动画实战]]（§四 音量包络驱动、§五 升级方案与六条同步规则）、[[Voice-Live系列05：两类数字人头像]]（卡通形象只能客户端自渲染）
- **首次出现**：2026-09-12
- **最近更新**：2026-11-23
- **置信度**：0.6
- **状态**：active
- **证据类型**：实测经验
- **复核**：2026-11-23 降级——依据：原来源标题在 git 历史中从未存在，实际出处是 [[Blender系列04：人物面试动画实战]]；该文 §五 明确写"已核对文档、未接入影片"，viseme 驱动的客户端渲染只是方案，原 Claim 写成"客户端接入实证"说强了，正文列的三条要点也不是文中的六条规则

> viseme 事件流由云端语音 API 下发、渲染在本地执行，时间轴（Voice Live 的 `audio_offset_ms`，Azure Speech SDK 的 100 纳秒 tick）是跨位面的耦合接口（相关判据框架见 [[compute-locus-spectrum]]）。**已实做的**是简化方案：60 Hz 音量包络驱动一个开口形态键，说话时张合、停顿时回落，但不认发音，闭唇、圆唇都做不出来，这就是简化口型与精细口型的分界。**只核对了文档、未接入的**是精细方案：Azure Speech 输出 viseme ID 和 55 项面部系数（60 FPS，进 24 fps 要换算），事件按音频时钟对齐，不能用网络回调到达时间当动画时间。文中总结的六条同步规则：① 一次合成是一个完整版本（台词、参数、WAV、事件、音频哈希一起存档）；② 锁定声音之后再定嘴型；③ 音频剪辑与事件用同一个时间映射；④ 区分片段起点和发声起点；⑤ 统一视频时间基准（第 1 帧对应 0 秒）；⑥ 最终合成后再查偏移。其中 ④ 引用的是本片的实际数据（片段起点与发声起点差 0.01 秒）。卡通形象（非人类比例）两类 Voice Live 头像都不支持，出路是客户端拿 viseme 时间轴自渲染。
