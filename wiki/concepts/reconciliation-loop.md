# Reconciliation Loop（调和循环）

## 摘要

调和循环反复做一件事：读系统的**真实状态**，和期望状态比对，修掉偏差。Kubernetes controller 是最出名的实现，云资源治理守护、沙箱与快照的回收对账器也是同一结构。它是 [[negative-feedback]] 在运维与平台工程里的形态：可靠性不来自某一次操作做对了，而来自"一直在读当前状态、一直在修"。

实践中最容易出错的是方向。一个只从自己的记录出发去清理的循环，永远看不见没有记录的东西——数据库回滚、分配成功但写库前进程被杀，都会留下"实际存在、账上没有"的资源。所以完整的回收要两个方向都有：从记录往外清到期的，从实际资源往里找孤儿。

## Claims

### Claim: 事件路径负责"及时"、定时扫描负责"全"——可靠性来自两路都读当前状态再比对修正；修复要幂等，调节器只自动修它能安全修的，其余交给人

- **来源**：[[Azure资源标签守护：事件订阅与定时扫描的自动修复]]
- **首次出现**：2026-10-26
- **最近更新**：2026-11-14
- **置信度**：0.75
- **状态**：active

> Event Grid 事件让检查在资源变更后及时发生，定时扫描看到某一时刻的全量状态；两路都"读真实状态 → 比对规则 → 修偏差"。修复幂等：只提交需修正的键、已合规直接返回、写后再读、资源已删就结束不重建。被策略禁用的 Key 认证只检测并交接、不自动改回；告警改为状态型、持续未恢复才通知、恢复不发信。未知资源类型先报错而非静默跳过。原为 [[feedback-loop]] 的运维域实例 Claim，建页后归口本页。

### Claim: 回收要两个方向——会话层从状态库往外只能清有记录的，状态库没有记录的沙箱与删记录后的快照镜像都会泄漏；补一个从外往里的对账器两者合起来才完整

- **来源**：[[AKS-Agent-Runtime系列05：会话生命周期与回收]]
- **首次出现**：2026-11-12
- **最近更新**：2026-11-14
- **置信度**：0.8
- **状态**：active

> 会话层维护循环每 15 秒遍历状态库，清三种：保留期到了、所属应用被删了（实测删应用后 14 秒清掉两个暂停会话的沙箱与快照记录）、准备阶段卡住超过"操作超时 + 10 分钟"。实测两个漏洞：① 直接调 OpenSandbox API 建一个带真实会话同款两个标签、不设 TTL 的沙箱，模拟状态库丢记录——6 分钟约 24 个周期无人管；代码里有"按标签盘点所有沙箱"的函数，但没有任何地方调用。Ephemeral 有 TTL 兜底，Durable 会一直占一个 Kata VM。② "删 checkpoint"只删 OpenSandbox 里的快照记录、不动 ACR 镜像：删应用后每个会话还留 5~6 个 tag，三天环境另有 3 个早已不存在的会话留着快照仓库。补的对账器：盘点带"会话 ID + 应用 UID"两个标签的沙箱与 ACR 快照仓库 → 拉会话层认识的全部会话 → 应用不存在或会话层不认识的算孤儿 → 删前重读。默认只出报告，加 `--apply` 才删，复查后剩余沙箱全部有主。会话层管"有记录、该到期的"，对账器管"实际存在、没记录的"。

### Claim: 对账删除要刻意保守——只认归属标签齐全的资源、安全期长于"操作超时"、删前按 ID 重读、旧 tag 只摘不删 manifest、先跑几天报告模式再开删除

- **来源**：[[AKS-Agent-Runtime系列05：会话生命周期与回收]]
- **首次出现**：2026-11-12
- **最近更新**：2026-11-14
- **置信度**：0.75
- **状态**：active

> 只看一个标签或按名字推断归属都容易误删，预热池里未分配的沙箱、别的系统建的沙箱一律不碰。比安全期年轻的跳过——它可能正处在"已分配、还没写库"的窗口（参考实现用操作超时 + 10 分钟）。同一 digest 可能挂多个 tag（见过同一会话两个大小完全一样的 tag），按 tag 删 manifest 可能把还在引用的那个一起删；摘掉 tag 后无 tag manifest 交给 ACR 保留策略（需 Premium SKU）。对账器处理的是少见的不一致、不在关键路径上，按天跑就够，但一定要有。

### Claim: 快照仓库是回收里增长最快又最没人看的部分——每次 checkpoint 或暂停多一个 tag，要单独定每会话保留几个、会话删除连仓库删、配 untagged manifest 保留策略

- **来源**：[[AKS-Agent-Runtime系列05：会话生命周期与回收]]
- **首次出现**：2026-11-12
- **最近更新**：2026-11-14
- **置信度**：0.7
- **状态**：active

> 每份快照镜像在 ACR 显示 1.46 GB，其中 34 层是共用的基础镜像，真正新增的最后一层约 67 MB；但 tag 随轮次线性增长，而会话层只删快照记录。参考实现文档也写明 snapshot registry 的保留与清理需要运维自己配。

### Claim: controller 的周期复查也是调和——Agent CRD controller 每 20 秒按 tag 重新解析 skills 包 digest，tag 被挪动时 Pinned 只在 status 告警、Track 生成新 revision

- **来源**：[[AKS-Agent-Runtime系列07：Agent的类型、注册与发现]]
- **首次出现**：2026-11-13
- **最近更新**：2026-11-14
- **置信度**：0.7
- **状态**：active

> 往同一个 `reviewer:v1` 推新内容后 28 秒内两个 agent 都有反应：Pinned 的 revision 仍指向原 digest，status 多一条 `bundleTagMoved` 写明钉住哪个、tag 现在指向哪个；Track 自动生成新 revision 指向新 digest，旧 revision 保留、在用的会话不受影响。期望状态（spec + 策略）与真实状态（registry 里 tag 当前指向）的比对是同一结构；区别在于修偏差的动作由策略决定是"告警交给人"还是"自动跟随"——与标签守护"只自动修能安全修的"同一判断。
