# 题库：个人知识编译（PKC）

配合 [[pkc]] 使用，按站点分组。题型：**场景**、**辨析**、**解释**。答案是参考要点，说出主要意思即可。

## 第 1 站 · 问题：日记写入与消费的错配

### Q1 · 解释

**问**：日记"写入与消费的结构错配"指什么？

**答**：日记按时间线写，却按主题用；线性增长没有网络效应，大多数笔记写完就沉底，需要时找不到、连不起来。

**出处**：[[personal-knowledge-compiler]]

### Q2 · 解释

**问**：LLM Wiki 模型里，LLM 的角色是什么？

**答**：维护者而不是问答者——像 Wikipedia 编辑一样把知识编译成页面并持续维护。一句话："RAG = search，LLM Wiki = writing a book"。

**出处**：[[llm-wiki]]

### Q3 · 解释

**问**：PKC 的四层知识模型是什么？各层回答什么问题？

**答**：Concept（是什么，声明式知识）、Method（怎么做，步骤化过程知识）、Decision（为什么这么选，选型论证）、Typed Relations（怎么关联，类型化的关系边）。

**出处**：[[personal-knowledge-compiler]]

### Q4 · 解释

**问**：PKC 从"提取 → 记录"升级成完整循环，靠的是哪几项改进？

**答**：实践反馈闭环（方法 → 实践 → 置信度回写）、知识成熟度模型、决策层、类型化关联、跨切面查询——变成"提取 → 验证 → 演进 → 查询"。

**出处**：[[personal-knowledge-compiler]]

## 第 2 站 · 选择：编译式 wiki 而不是 RAG

### Q1 · 辨析

**问**："LLM Wiki 和 RAG 合并成一个企业方案效果最好。"对吗？

**答**：对个人知识库不对。两者是不同范式：wiki 是"编译一次、持续维护"，RAG 是"每次查询重新检索"。原计划把两者合并成 Azure 企业方案，实际用了 wiki 后发现强行合并增加复杂度却没增加核心价值，已取消。

**出处**：[[wiki-over-rag-for-personal-knowledge]]

### Q2 · 解释

**问**：独立基准里，图在哪些地方赢、哪些地方不赢？

**答**：图赢在 multi-hop 推理、时间推理、跨语料综合；简单事实查找不赢（纯向量更好，图只添冗余上下文），而且混合方法永远赢过纯图。

**出处**：[[wiki-over-rag-for-personal-knowledge]]

### Q3 · 解释

**问**：qmd 和 Foundry IQ 的定位有什么不同？

**答**：qmd 是"在自己设备上搜自己文件的最好办法"（BM25 + 向量 + 重排）；Foundry IQ 是企业级 agentic retrieval（LLM 驱动查询分解、多源并行检索）。

**出处**：[[rag-architecture-comparison]]

### Q4 · 解释

**问**：为什么说 LLM Wiki 有"知识复利"？

**答**：RAG 每次查询都从原始文档重新检索碎片，质量受分块策略限制；wiki 的页面是已经综合、交叉引用过的，好的回答还能写回 wiki，越用越好。

**出处**：[[llm-wiki]]

## 第 3 站 · 存储：不存事实，只存论断

### Q1 · 解释

**问**："不存事实只存论断"是什么意思？

**答**：不写"X 是 Y"，而写"根据来源 A，X 可能是 Y（置信度 0.8）"。承认知识的不确定性，同一问题可以有多条置信度不同的论断共存。

**出处**：[[claim-based-schema]]

### Q2 · 解释

**问**：Claim 有哪几种状态？怎么流转？

**答**：active（正常）、conflicting（发现矛盾证据）、outdated（被新证据取代）、stale（太久没更新，等待复核）。stale 经复核后回到 active，或转为 outdated、conflicting。

**出处**：[[claim-based-schema]]

### Q3 · 辨析

**问**："60 天没更新的 Claim 都是过时的。"对吗？

**答**：不对。stale 只表示"该复核了"，不代表错了。理论与方法类结论不随时间过期，复核后标为长效、不再按日期标 stale；产品与实测类才需要定期按证据复核。

**出处**：[[claim-based-schema]]、[[pkc]]

### Q4 · 解释

**问**：置信度按什么规则调整？

**答**：3 个以上独立来源支持加 0.1；有实验或实践验证到 0.7 以上；来源间矛盾标 conflicting 等人裁决。同一个系列的几篇文章不算独立来源。

**出处**：[[claim-based-schema]]

## 第 4 站 · 流程：从日记到概念页

### Q1 · 解释

**问**：一篇新文章进 wiki 的完整链路是什么？

**答**：每天的 harvest 循环发现新文章、入待提取队列 → `/extract-knowledge` 建页或把论断注入已有页 → 不建页的裁决写进 HOLD 账本，防止下次被重复提出 → 导出图谱、更新索引。

**出处**：[[Loop-Engineering实践：知识库外循环]]、[[personal-knowledge-compiler-workflow]]

### Q2 · 解释

**问**：一个技术概念要单独建页，需要同时满足哪三条？

**答**：在文章里被定义或深入解释（不只是提到）；是某技术领域的基础性概念（不是 API、JSON 这类通用词）；被 2 篇以上文章引用，或是其他概念页的理论基础。不确定时不建页。

**出处**：[[pkc]]

### Q3 · 辨析

**问**："一个维护良好的 wikilink vault 和 GraphRAG 没什么关系。"对吗？

**答**：不对。它已经是 80% 的 GraphRAG 索引：写下双方括号链接的那一刻，实体消解就完成了，没有自动抽取的模糊合并和沿跳数复合的误差。

**出处**：[[personal-knowledge-compiler]]

### Q4 · 场景

**问**：一篇文章里有客户名称、内部代码路径和真实面试题。能直接进 wiki 吗？

**答**：不能。进 git 的内容默认脱敏：改成通用示例和相对表述；私人日记和私人目录的内容不提取进 wiki；确需保留的信息要先和本人确认。

**出处**：[[pkc]]

## 第 5 站 · 记忆与规则：放哪一层

### Q1 · 解释

**问**：Claude Code 的六层记忆是哪六层？关键区分是什么？

**答**：Settings（强制配置，客户端执行）→ CLAUDE.md + Rules（行为指导，Claude 遵循）→ Auto Memory（自主笔记，跨 session）→ Session Transcripts（对话历史）→ Skills / Agents / MCP（按需加载的扩展）→ App State。关键区分：Settings 机械执行，CLAUDE.md 理解遵循，Memory 按需回忆。

**出处**：[[claude-code-memory-system]]

### Q2 · 场景

**问**：一条"必须用相对路径写链接"的规则写在 auto memory 里，却经常被忽略。为什么？怎么办？

**答**：memory 是以"可能相关、酌情参考"的语气注入的，模型把它当可选参考。行为规则要提权到 CLAUDE.md 或 rules；被反复违反的，再考虑做成 hook（代码级强制）。

**出处**：[[claude-code-memory-system]]

### Q3 · 解释

**问**：Claude Code 和 GitHub Copilot 从不同方向得出了同一个分层，是什么？

**答**：会过时、可以被核对的事实放记忆；必须遵守的规则放进 git 里的指令文件。Copilot 的 Dreaming 对 instructions / skills 开 PR，本质上就是把"记忆提权到指令文件"自动化了。

**出处**：[[claude-code-memory-system]]

### Q4 · 解释

**问**：文件记忆和后端记忆（如 Copilot Memory）各有什么取舍？

**答**：后端记忆胜在团队共享和自动遗忘（过期机制），但内部字段不可见、没有 diff；文件记忆胜在可见、可 diff、可回滚，但没有自动过期，要定期人工审查。

**出处**：[[agent-memory-lifecycle]]

## 第 6 站 · 鲜活：内循环与外循环

### Q1 · 解释

**问**：外循环的最小内核是什么？哪一个是分水岭？

**答**：自动发现 + workflow + 重复（定时）+ 跨轮记忆。自动发现是分水岭：任务靠人喂进来的不是外循环，系统自己发现该做什么才是。

**出处**：[[loop-engineering]]

### Q2 · 解释

**问**：无人值守的外循环需要哪三个互相独立的部件？

**答**：触发器（cron 只是闹钟，每次起一个无记忆的新会话）、记忆（LOOP_STATE.md，待办快照，也是人工审阅入口）、trace（loop-run-log.md，只追加的事件流）。

**出处**：[[loop-engineering]]

### Q3 · 辨析

**问**："外循环越自动越好，应该让它直接改 wiki 的结论。"对吗？

**答**：不对。安全总纲是"管道自动化，判断留给人"：有 ground truth 的确定性管道（坏图、死链、索引过期）自动执行；该提取什么、Claim 对不对、冲突怎么解这类语义判断只提议，等人拍板。

**出处**：[[loop-engineering]]

### Q4 · 解释

**问**：什么样的工作流适合做成外循环？

**答**：重复且有节奏；大部分步骤有 ground truth；需要品味的判断点能干净地隔离出来，收敛成几条待审，人只在这几处花注意力。

**出处**：[[loop-engineering]]

## 第 7 站 · 图：知识图的三种含义

### Q1 · 解释

**问**："graph engineering"一词有哪三种含义？哪一种有研究与基准背书？

**答**：编排图（类型化节点、条件转移，不新）、循环网络（把多个循环连成网）、类型化知识图。只有知识图这一含义有十年研究与独立基准背书。

**出处**：[[graph-engineering]]

### Q2 · 解释

**问**：什么时候值得上图（graph），而不是用单循环？

**答**：复杂任务加高并发时才上：经验法则是任务有 3 个以上互相独立的验证步骤加复杂条件路由。而且单轮通过率低于约 50% 时并行图比顺序循环更贵，该盯的是每次成功完成的成本。

**出处**：[[graph-engineering]]、[[loop-engineering]]

### Q3 · 解释

**问**：为什么说"循环之图必须有图外的锚点"？

**答**：如果审计循环拿来对账的数字来自被审计的同一批系统，图就是环形的——一切一致，却无一被验证。需要不可争辩的测量、冻结不许调的规则等图外锚点，持久的轴是 ungrounded vs grounded。

**出处**：[[loop-engineering]]

### Q4 · 解释

**问**：企业 Ontology 把数据从"可查询"升级到"可理解、可推理、可行动"，指什么？

**答**：在物理统一但语义碎片化的数据之上，定义统一的业务对象和关系，并通过动作类型实现行动闭环；AI 在语义明确的对象图上推理，而不是直接读原始表。Fabric IQ 的 Ontology 目前仍是 preview。

**出处**：[[enterprise-ontology]]
