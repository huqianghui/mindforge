# Resident Instance vs Session Scheduling（常驻实例与会话调度）

## 背景

在 AKS 上自建 agent runtime，有两种形态，两种都已做过初步实验：

- **会话调度**（系列 01~11 的参考实现）：控制面收到消息，按会话从预热池领一个 Kata 沙箱，跑完一轮做 checkpoint，空闲暂停，保留期到就回收。状态的单位是会话，沙箱只是借来的执行环境。实测覆盖了生命周期、快照恢复、三副本高可用、出站逐请求授权、模型接入、OBO 身份。
- **常驻实例**（系列 12、13 的常驻实现）：每个人一个 agent 实例，StatefulSet 单副本加 Kata，状态和私有记忆都在一块 100Gi 的 HOME 盘上，暂停就是缩到 0、盘保留；Portal 只写 CRD，operator 往 AKS 和 LiteLLM 两边单向投影。实测是 helm template 渲染加整套平台装进 AKS 逐项核对。

两种形态都把 harness 整个关进 Kata、凭据留在沙箱外、模型请求只走网关、企业资源令牌不进 Pod。分歧在三处：**状态跟着谁走、出站默认开还是默认关、记忆放在哪**。这一页把两者的取舍、选法，以及往下深入对比和找客户场景时该看什么，放在一起。

## 选项分析

### 选项 A：会话调度（状态跟着会话走）

- **优势**：空闲不占 VM，算力按用量付；沙箱随时可换，控制面能做多副本（lease + fencing，硬杀约 15 秒接管）；恢复时出站白名单按**当前**权限重新下发，撤销对暂停中的会话同样生效；调用方可以是人、渠道、定时任务或另一个 agent。
- **劣势**：每轮 checkpoint 两次 commit 各 30~40 秒，恢复约 10 秒且进程是新的；快照镜像要清理、会话库和沙箱要对账；会话控制面几乎全要自己写；会话删掉什么都不剩，没有按人归属的长期记忆，也没有给人用的原生界面。
- **适用条件**：多个调用方按次调用；任务是执行者型（推代码、改工单、调配置），需要逐请求授权；事件驱动、批量、夜间任务。

### 选项 B：常驻实例（状态跟着人走）

- **优势**：不需要 checkpoint，Pod 没了盘还在，恢复就是挂回盘；私有记忆和团队 Skills 天然有地方放；用户直接打开 harness 原生界面，加上 Terminal 和 Desktop 两个入口，人能随时接手；运维面相对简单（没有会话库、快照仓库、对账器）。
- **劣势**：算力按人常驻（主容器 4 vCPU + 桌面 0.5 vCPU / 人，一百人就是 450 vCPU 请求量），没有空闲自动休眠；单副本，只支持健康源冷迁移，不做故障切换；`Retain` 不等于备份；出站公网默认放行加黑名单，挡不住新的外传目的地；高风险动作没有审批点，月度预算是软上限，人不在时可能跑满一整晚。
- **适用条件**：agent 跟着一个固定的人，状态要跨周跨月；人数有限、岗位价值高（值班、核心开发）；以读为主的助手场景。

### 选项 C：混合形态——轻量常驻入口 + 会话执行池

- **优势**：常驻部分只负责"这个人是谁、以前定过什么、团队批准了哪些 skills"，不必一直占 4 vCPU；长任务、批量和事件触发的工作交给会话执行池，按会话领沙箱、做 checkpoint、受逐请求授权管控。
- **劣势**：中间两个接口目前两边都没有：执行池领任务时带上发起人身份和记忆的只读视图；任务结束只回写结论、不回写原始输出。
- **适用条件**：人多、大部分时间闲着，但又需要按人的长期上下文。常驻实现的路线图上已有 Run / Session 层和共享 agent 池，后者照字面看就是会话执行池，两条路线在往这里走。

## 决策结论

- **选择**：按三个问题依次判断，不预设一种形态。
  1. **agent 跟着谁？** 很多调用方按次调用 → 会话调度；跟着一个固定的人 → 往下问。
  2. **状态要活多久？** 一个任务内就够 → 会话调度的 Ephemeral 会话；要跨周、跨月记得这个人 → 往下问。
  3. **算力能不能按人常驻？** 人数有限、岗位价值高 → 常驻实例；人多且大部分时间闲着 → 混合形态。
- **两条不随形态变的底线**：要对企业资源做写操作，出站就得收成只剩网关一条路、按资源加动作逐请求授权；令牌永远不进沙箱。
- **理由**：两种形态各缺的那一块正好是对方已经有的——会话调度缺按人的记忆和入口，常驻实例缺空闲回收、多副本和逐请求授权。选择本质是"状态的单位"和"控制点的位置"，不是谁更先进。
- **放弃理由**：不把常驻实例当成会话调度的简化版（它省掉的快照与对账，换来的是按人常驻的算力和更弱的出站控制）；也不把会话调度当成常驻的上位替代（它没有长期记忆层，给人用的体验要另做）。
- **前提假设**：① 常驻实现的路线图（Run / Session 层、共享 agent 池）照计划推进，否则混合形态的接口要自己补；② Kata 节点的容量与价格不变——若按需 VM 冷启动显著变快或变便宜，会话调度的成本优势会被放大；③ 常驻侧的出站仍是黑名单模型——若它引入逐请求授权，第 2、3 问的分界要重画。

## 深入对比的指导

下一轮对比按下列维度做，每项都写明"怎么测、测到什么算结论"。前两次实验已经覆盖的打 ✅，其余是下一步要补的。

**状态与恢复**
- ✅ 恢复耗时与恢复后剩什么：会话调度 9.5~11.2 秒、进程是新的；常驻挂回盘即可。
- ☐ 常驻实例的 HOME 盘故障与节点故障：强制删 Pod、节点 NotReady 时 RWO 盘多久释放、旧挂载是否真的放手（对应系列 06 的"卡住又醒来的旧主"）。
- ☐ 备份与恢复演练：namespace 被删后数据能否找回，依赖 StorageClass 回收策略与快照方案。

**成本**
- ☐ 同一组用户、同一周负载下两种形态的 vCPU·小时：常驻按请求量常驻，会话按实际轮次与暂停阈值。给出盈亏平衡点——每人每天活跃多少小时以下，会话调度更便宜。
- ☐ 混合形态的常驻入口最小能压到多少（去掉桌面、换 headless 浏览器之后）。

**治理**
- ✅ 出站模型差异：常驻公网默认放行 + 黑名单（SNI，不解密），会话调度默认拒绝 + 逐请求授权。
- ☐ 常驻实例接入出站网关的代价：只把写操作收进网关时，读操作的公网放行还剩多少外传面。
- ☐ 高风险动作审批：两边都没有，补在哪一层（网关、会话层还是 harness 权限档位）。
- ☐ 容量配额：一个 Team 或一个人最多几个 Agent、总共占多少 Kata 容量，两边都没有上限。

**可观测与追溯**
- ✅ 常驻实现的五类日志（管理操作、Agent 输出、模型调用、出站连接、平台组件）没有共同的会话或轮次 ID，集群上实际只有模型调用一条线有数据。
- ☐ 按轮次 ID 端到端追溯：harness 或会话层每轮生成 ID，带进模型请求元数据和出站请求头，两个网关都记下来，验证一次副作用能否倒查到哪一轮。

**记忆**
- ✅ 常驻实现的私有记忆规则（先查再答、存结论不存原文、记忆不授予权限、从失败学习要过固定检查、私有记忆不外泄）。
- ☐ 混合形态下执行池拿到的记忆视图：只读、按任务裁剪、结论回写的格式与审核。

## 客户机会识别

客户场景不按"要不要 agent"分，而按上面三个问题的答案分。下面每一类写明识别信号、适合的形态，以及从实验里看到的、需要补的那一块——后者往往就是方案工作的切入点。

1. **按人配专属工程助手（值班、核心开发、架构师）**
   - 信号：希望 agent"记得我"、跨天推进、人下线后继续做；人数在几十人以内；要直接用现成 harness 的原生界面。
   - 形态：常驻实例。
   - 要补的：备份方案、出站外传审计、写操作进网关、按人的预算硬上限。
2. **多渠道调用的执行型 agent（工单处理、代码修复、配置变更、CI 触发）**
   - 信号：调用方是 Teams、定时任务、流水线或别的 agent；每次任务独立；动作要对企业资源做写操作，安全团队要求逐请求可批可撤。
   - 形态：会话调度。
   - 要补的：会话控制面（最重的自研）、对账器、快照仓库清理、审批点。
3. **人多但大多数时间闲着的全员助手**
   - 信号：几百人以上、单人日活跃时间短，但又希望按人保留偏好与历史。
   - 形态：混合形态。
   - 要补的：常驻入口的瘦身、执行池带身份与记忆视图的接口、结论回写。
4. **已经装了常驻平台、开始碰到治理问题**
   - 信号：两个控制台（Portal 与 LiteLLM）改配置互相覆盖；用量看不到；出了问题追不到是哪一轮；安全团队问"agent 夜里推了什么"。
   - 形态：不换形态，补治理。
   - 要补的：Portal 唯一写入口与只读用量页、日志接通（观测 chart、审计日志、Kata 节点采集）、轮次 ID、出站逐请求授权与审批。
5. **还在 Hosted 与自建之间犹豫**
   - 信号：能用自写 loop、沙箱规格在托管上限内、出站不需要逐请求批准。
   - 形态：先回到 [[foundry-agent-type-selection]]——满足这些条件时托管更省事，两种自建形态都不必上。

> 以上识别信号来自两次实验的结论推导，还没有拿真实客户场景逐条验证；用来引导需求访谈，不是现成的方案清单。

## Claims

### Claim: 两种形态的根本分歧是"状态跟着谁走"——常驻实例的状态就是一块 RWO HOME 盘，会话调度的状态是一串快照加状态库

- **来源**：[[AKS-Agent-Runtime系列12：常驻实例与会话调度]]、[[AKS-Agent-Runtime系列05：会话生命周期与回收]]
- **首次出现**：2026-11-16
- **最近更新**：2026-11-18
- **置信度**：0.8
- **状态**：active
- **证据类型**：实测经验

> 常驻实例：StatefulSet 只允许 0 或 1 个副本，`volumeClaimTemplates` 一块 100Gi RWO 盘挂在 HOME，两条 `Retain`；Agent CRD 的 `suspended` 为 true 时缩到 0、去掉入口路由、PVC 保留，设回 false 后 Pod 重建挂回同一块盘，harness 从盘上读回会话。没有空闲自动暂停，只有显式暂停。会话调度：领预热 Pod 约 1.2 秒，一轮之后 checkpoint 31~41 秒，空闲到阈值再 commit 一次后删 Pod，回来时从镜像新建 Pod 9.5~11.2 秒、进程是新的。常驻省掉了快照与对账，代价是算力按人常驻、单副本只有健康源冷迁移、namespace 被删时 PVC 跟着删（"持久的 HOME 不是备份"）。装进 AKS 后核对：Kata 调度、资源请求、盘规格都与渲染结果一致。

### Claim: 出站的两种默认对应 agent 的两种用途——助手型公网默认放行加黑名单、风险在外传；执行者型默认拒绝加逐请求授权；要写企业资源就必须收进网关

- **来源**：[[AKS-Agent-Runtime系列12：常驻实例与会话调度]]、[[AKS-Agent-Runtime系列04：出站治理与逐请求授权]]
- **首次出现**：2026-11-16
- **最近更新**：2026-11-18
- **置信度**：0.75
- **状态**：active
- **证据类型**：实测经验

> 常驻实现渲染出的 NetworkPolicy 放行集群 DNS、Istio 控制面、AI 网关 4000 端口、一个内部地址，以及 `0.0.0.0/0` 减去三个私网段和 IMDS；AgentPolicy 网络部分只有三个黑名单加一个内网白名单，按域名拉黑靠 SNI、不解密 HTTPS、对 ECH 不保证。令牌不在 Pod 里，直接出站拿到的只是公开内容，所以风险在被提示注入后把内部工具拿到的东西发到公网，黑名单只能挡已知目的地，靠审计加事后处置。会话调度侧默认拒绝、只剩出站网关，每个请求核对"申请 ∩ 批准 ∩ 发布"。只读工具走 Broker、其余直接出站的组合只适合以读为主的助手。

### Claim: 常驻实例的入口分三层且只对 owner 开放——Agent UI 对话、Terminal 直接操作环境、Desktop 看和接手浏览器；exec 被准入策略拒绝、Kata Pod 无法 port-forward，Terminal 是唯一正式 shell 入口

- **来源**：[[AKS-Agent-Runtime系列13：Runtime管控台与LiteLLM的分工]]、[[AKS-Agent-Runtime系列12：常驻实例与会话调度]]
- **首次出现**：2026-11-17
- **最近更新**：2026-11-18
- **置信度**：0.75
- **状态**：active
- **证据类型**：实测经验

> 同一个 Pod 三个容器：harness 主容器、带浏览器的桌面边车、logger。ValidatingAdmissionPolicy 对实例 namespace 的 `pods/exec` 一律返回 false，集群里 `kubectl exec` 在准入阶段被拒；`port-forward` 连不上，因为 Kata Pod 的端口在虚拟机里、kubelet 在宿主侧找不到——平台管理员也没有别的路进这台机器。Terminal 是 ttyd 网页 shell，走独立入口路由，不经 exec；Desktop 是 noVNC 上的 Chrome，agent 经本机 CDP 操作，人可以替它过验证码或 MFA。三个入口都先过 Entra、再过 ingress 按路径的 owner 检查，管理员能看到所有 Agent 但进不去别人的工作区。两处代价：harness 界面密码就是实例的 API key（chart 和启动脚本都校验两者相同），拿到界面密码等于拿到 API 凭据；Desktop 的 Chrome 以 `--no-sandbox` 启动，隔离只靠 Kata 与 owner 检查。桌面和终端在 chart 里都能单独关掉。

### Claim: 两种形态会走到同一个样子——轻量常驻入口加会话执行池；中间要补的接口是执行池带发起人身份与记忆只读视图、任务结束只回写结论

- **来源**：[[AKS-Agent-Runtime系列12：常驻实例与会话调度]]
- **首次出现**：2026-11-16
- **最近更新**：2026-11-18
- **置信度**：0.55
- **状态**：active
- **证据类型**：设计推论

> 常驻实现路线图上的两项——Run / Session 层（长任务检查点与恢复、权限随任务收放）和共享 agent 池（无界面、队列驱动、多副本可互换、HOME 随用随弃、一把网关 key 按任务归因、没有入站路由）——后者照字面就是会话执行池。会话调度这边缺的是按人归属的长期记忆和给人用的入口，常驻实例的盘上已经在做。判断依据是两条路线图的对照，混合形态尚未实现。

### Claim: 管理员也作为一个 agent 运行，但权限由平台在 agent 之外收窄——没有 exec 例外、不能读写 Secret、改不了自己的登录元数据，针对它的准入 webhook 都是 fail-closed

- **来源**：[[AKS-Agent-Runtime系列12：常驻实例与会话调度]]
- **首次出现**：2026-11-17
- **最近更新**：2026-11-18
- **置信度**：0.7
- **状态**：active
- **证据类型**：实测经验

> 平台装好后 Operator 自动起一个 Hermes 实例做运维，带一组运维 skills，负责诊断和管理同一 Operator 下的所有普通实例；对其他平台 namespace 只有可选的只读诊断。与"记忆不授予权限"同一思路：agent 再能干，权限边界也由平台划定，不靠 agent 自觉。
