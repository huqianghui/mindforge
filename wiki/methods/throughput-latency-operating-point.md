# 工作点读数法（Throughput-Latency Operating Point）

## 摘要

解读任何推理性能 benchmark（芯片、框架、模型 API）时的防误读方法：厂商公布的每个数字都是**吞吐—延迟曲线上某个工作点**在**某种口径**下的读数，直接拿数字比大小必然误判。同一对硬件能同时给出 1.9× 和 104× 两套不矛盾的数字（Jalapeño vs GB300），同一个模型能同时宣称"Prefill 快 7.6×"和账单只降三成（内核级 vs 端到端）——方法的核心动作是：先定位工作点、再还原口径与基线、区分组件级与端到端读数，最后换算到自己的负载形状。

两次独立实践验证：OpenAI Jalapeño 首测解读（2026-08-26，硬件对比场景）与 Qwen3.8/GLM-5.3-Flash 六层降本解剖（2026-08-31，架构降本与价格战场景）。2026-08-30 曾裁决 HOLD 归口 Claims，2026-09-04 因第 2 次实践命中复核阈值升格为方法页。

## 适用条件

- **前置依赖**：拿到的性能数字附带（或可以追问到）测试条件——并发数、功耗口径、序列长度、缓存状态。
- **适用场景**：芯片对比（ASIC vs GPU）、推理框架选型（vLLM/SGLang 压测）、模型 API 价格战归因、厂商发布会数字核验。
- **不适用场景**：数字来源完全不透明且无法追问口径时——此时唯一正确动作是标注"口径未知"拒绝比较，而非套用本方法硬读。

## 步骤

### Step 1: 定位工作点

- **输入**：厂商公布的性能倍数（"1.9×"、"104×"、"3 倍"）
- **操作**：判断该数字取自吞吐—延迟曲线的哪个点——峰值吞吐（各自开到最大产能）、最低延迟（单用户最快）、还是 matched 约束点（固定一方指标比另一维）
- **输出**：数字的语境标签
- **判断标准**：能回答"这个数字回答的是什么问题"——极限产能 / 单用户体验 / 相同约束下的并发承载，三者不可互换

### Step 2: 还原口径与基线

- **输入**：Step 1 标注过的数字
- **操作**：追问三个口径——比较基线是什么（对手最优 or 自己的初始基线）、分母是什么（per-chip or per-kW、峰时 or 谷时价）、统计范围是什么（mixed TPS 含输入+输出）
- **输出**：口径还原后的可比数字
- **判断标准**：GLM"3 倍端到端"还原后=相对相同硬件初始基线的自我提升；Jalapeño per-kW 口径中功耗差（700W vs 1400W）本身贡献一半账面优势——**度量口径即立场**

### Step 3: 区分组件级与端到端读数

- **输入**：还原口径后的数字
- **操作**：判断数字测的是单个组件（注意力内核、单算子）还是完整请求链路（含 MoE、输出层、通信、调度）
- **输出**：数字的传导折扣预期
- **判断标准**：Qwen QSA "Prefill 7.6×/Decode 4.9×" 是注意力模块内核级读数，完整 API 请求不会同比例快；"训练 1/9 FLOPs"=激活 1/3 × token 1/3 的乘积而非单一技术

### Step 4: 换算到自己的负载形状

- **输入**：语境明确的数字集合
- **操作**：把自己负载的关键参数（前缀稳定性、并发水平、峰谷时段分布、重试率）代入，算实际相关的那个工作点
- **输出**：选型结论
- **判断标准**：结论落在"每成功任务成本"而非"每百万 token 单价"——prompt 结构稳定选缓存命中价最低的（DeepSeek $0.007），交互式低并发看最低 TBT，批量高并发看 matched 约束下的吞吐

## 决策点

| 条件 | 选择 | 理由 |
|------|------|------|
| 数字是"NX 倍于竞品" | 先问工作点 + 功耗/并发口径 | matched 约束点读数（104×）绝不能读成整体性能倍数 |
| 数字是"NX 倍提升" | 先问基线是谁 | 相对自己初始基线的提升无法横向比较 |
| 数字来自论文/技术报告 | 区分内核级 vs 端到端 | 组件加速经过完整链路后必然折扣 |
| 数字无法还原口径 | 标注"口径未知"，拒绝比较 | 硬读比不读更危险 |

## Claims

### Claim: 同一对硬件可以同时给出 1.9× 与 104× 两套不矛盾的数字——它们是吞吐—延迟曲线上不同工作点的读数

- **来源**：[[OpenAI Jalapeño推理芯片——从ASIC基础到首测数据解读的AI推理硬件全景]]
- **首次出现**：2026-08-26
- **最近更新**：2026-09-04
- **置信度**：0.8
- **状态**：active

> 峰值 mixed TPS/kW（1.5~1.9×）=极限产能；最低 TBT（2.7~4.1×）=单用户最快解码；matched TBT 下的吞吐（53~104×）=把对手最快单用户速度设为共同约束后比较仍能承载的并发量。餐厅类比：104× 不是"上菜快 104 倍"而是"相同上菜速度下能服务的顾客数差 104 倍"。详版 Claim 归口 [[ai-inference-asic]] 与 [[hybrid-inference-framework-selection]]（08-30 注入）。

### Claim: 内核级读数 ≠ 端到端读数；"相对自己"的提升 ≠ 可横比的优势——第 2 次实践把方法从硬件对比扩展到架构降本归因

- **来源**：[[国内大模型新一轮架构与价格优化——Qwen3.8-Flash与GLM-5.3-Flash的六层降本解剖]]
- **首次出现**：2026-08-31
- **最近更新**：2026-09-04
- **置信度**：0.8
- **状态**：active

> 六层降本解剖通篇是读数法的第二场景实践：QSA"Prefill 7.6×"是注意力内核级而非 API 端到端；GLM"3 倍端到端"是相对相同硬件初始基线的自我提升；"训练 1/9 FLOPs"是激活 1/3 × token 1/3 的乘积读法；峰谷分时计费（DeepSeek 峰谷 2× 价差）把"何时测"也变成口径变量。方法的适用面由此从"芯片 benchmark"扩展到"架构优化的降价归因"——两个场景共享同一套动作：定位工作点 → 还原口径 → 区分层级 → 换算自身负载。

### Claim: 度量口径即立场——per-kW vs per-chip、峰时 vs 谷时，读任何厂商数字前先确认分母

- **来源**：[[OpenAI Jalapeño推理芯片——从ASIC基础到首测数据解读的AI推理硬件全景]]、[[国内大模型新一轮架构与价格优化——Qwen3.8-Flash与GLM-5.3-Flash的六层降本解剖]]
- **首次出现**：2026-08-26
- **最近更新**：2026-09-04
- **置信度**：0.75
- **状态**：active

> OpenAI 主张 per-kW（电力是数据中心第一约束——合理叙事，但 700W vs 1400W 的功耗口径贡献了一半账面优势）；DeepSeek 用峰谷分时把"什么时段"变成价格分母。口径选择既是工程叙事也是营销框架，两次实践中口径还原都改变了直接读数的结论方向。

## 实践记录

### Practice: 2026-08-26 — Jalapeño 首测解读（硬件对比场景）

- **应用场景**：解读 InferenceX 公布的 Jalapeño vs GB300 首测数据
- **实际结果**：成功——分离出三个工作点，避免把 104× 读成整体性能倍数
- **偏差与调整**：无（方法首次成形于此场景）
- **经验教训**：matched 约束点读数最有迷惑性，也是对交互式 serving 选型最相关的数字
- **置信度影响**：建立基线

### Practice: 2026-08-31 — 六层降本解剖（架构降本归因场景）

- **应用场景**：核验 Qwen3.8/GLM-5.3-Flash 官方技术报告与转写稿中的性能/成本数字
- **实际结果**：成功——纠正转写稿多处误读（GLM 比较对象是 GLM-4.5 非 5.2、QSA 非 "Quick Sparse Attention"、3 倍基线口径）
- **偏差与调整**：新增"内核级 vs 端到端"与"相对自己 vs 可横比"两个判别维度（硬件场景未覆盖）
- **经验教训**：架构降本场景的口径陷阱比硬件对比更多（训练成本折旧、限时价格、峰谷分时都掺进"降本"叙事）
- **置信度影响**：两条核心 Claims 由 0.75 升至 0.8（第 2 场景独立验证）
