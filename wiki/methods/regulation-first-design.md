# Regulation-First Design（调节优先设计）

## 摘要

用控制论的顺序设计 harness：先定义要维持稳定的被调节量（Regulated Variables），再识别把它拉偏的扰动、设计观测偏差的反馈通道、实现纠偏的调节器，最后才把这四步封装成 harness。传统做法是直接跳到"用什么框架、加什么 lint"，等于在没定义目标的情况下堆手段。

在 Vibe Coding 里，真正的被调节量只有两个：**需求对齐度**（系统做的就是用户要的）和**功能可见性**（用户能在界面上看到功能正确工作）。架构、模块划分、单元测试、端到端测试、CI 都是服务这两个目标的调节器。与 [[cybernetics-harness-design-sheet]] 的关系：那张表按控制论五层（可能性空间、共轭变换、负反馈、探索、控制能力）逐项检查一个 agent 的设计；本方法按调节回路的顺序组织一个项目的 harness，两者可以先后使用。

## 适用条件

- **前置依赖**：知道项目要交付的功能和关键界面
- **适用场景**：用 coding agent 推进的长期项目，尤其是"越改越乱""做出来不是我要的"已经出现时
- **不适用场景**：一次性脚本、没有用户可见行为的小任务

## 步骤

### Step 1: 定义被调节量

- **输入**：需求与关键界面
- **操作**：列出 3~5 个必须对齐的功能目标、关键 UI/UX 验收点
- **输出**：Regulated Variables 清单
- **判断标准**：清单里是用户能感知的结果，没有"代码质量""覆盖率"这类手段

### Step 2: 识别扰动

- **输入**：被调节量
- **操作**：列出模型理解偏差、技术复杂度、需求模糊区域等会把目标拉偏的来源
- **输出**：Disturbances 清单
- **判断标准**：每一项都说得出它会让哪个被调节量偏离

### Step 3: 设计反馈通道

- **输入**：扰动清单
- **操作**：自动化反馈（测试、lint、类型检查）与人工反馈（评审节点、验收时机）分开设计
- **输出**：Feedback Channels
- **判断标准**：每个被调节量至少有一条能发现偏差的通道

### Step 4: 实现调节器

- **输入**：反馈通道
- **操作**：按层放调节器——需求层（Spec、验收标准）、设计层（UI 稿、截图基线）、架构层（模块边界、API 契约）、实现层（测试集、CI）
- **输出**：Regulators
- **判断标准**：每类扰动都有一个专门对付它的调节器

### Step 5: 封装成 harness，按调节回路迭代

- **输入**：以上四步
- **操作**：每次迭代走一遍"设定目标 → agent 执行 → 观测反馈 → 计算偏差 → 改 prompt、补约束或人工介入"，直到偏差可接受；定期回顾并更新调节机制本身
- **输出**：可持续运转的 harness
- **判断标准**：失控时能按下面的诊断表定位是哪一环缺失

## 决策点

| 症状 | 可能的调节失败 | 修复方向 |
|------|---------------|---------|
| Agent 做的不是我要的 | 被调节量没有明确定义 | 补 Spec 与验收标准 |
| 功能做对了但 UI 不对 | 缺少视觉层反馈 | 加 UI 设计稿、截图对比 |
| 改一个地方坏了别处 | 缺少结构性调节器 | 加模块边界与回归测试 |
| 越改越乱 | 调节器多样性不足 | 增加调节机制的种类 |
| 约束本身过时了 | 缺少二阶调节 | 定期回顾、更新 harness |

## Claims

### Claim: 代码质量不是被调节量而是调节器——把手段当目标，是工程里最常见的调节失败

- **来源**：[[Vibe-Coding系列13：控制论指导Harness-Engineering]]
- **首次出现**：2026-05-07
- **最近更新**：2026-11-24
- **置信度**：0.7
- **状态**：active
- **证据类型**：实测经验

> 在 Claude Code 加 Vibe Coding 的项目实践里，本质要维持的只有需求对齐度和功能可见性两个；代码质量是维持前两者的手段，测试覆盖率是观测偏差的工具，架构一致性是降低扰动的结构设计。优化了覆盖率而用户要的功能没做对，就是把手段当成了目标。这是对我自己项目实践的归纳，换到没有用户界面的系统（后台服务、数据管线），"功能可见性"要换成对应的可观测结果。

### Claim: 很多"多智能体架构"本质上是多层调节层级——需求澄清和 UI 设计两层定义目标，架构、实现、运行时三层只是保护目标

- **来源**：[[Vibe-Coding系列13：控制论指导Harness-Engineering]]
- **首次出现**：2026-05-07
- **最近更新**：2026-11-24
- **置信度**：0.65
- **状态**：active
- **证据类型**：理论

> 人调节评估器、评估器调节规划器、规划器调节执行器、执行器调节模型输出，每一层的反馈来源不同（直觉与业务知识、验收标准与测试结果、架构约束、lint 与单元测试），这是控制层级而不是"agent 社会"。落到 Claude Code 的实际流程是六层：L0 人定义目标与最终验收；L1 需求澄清（PRD、用户故事、验收标准，人确认"就是这个"）；L2 UI 设计（设计稿、截图，人确认"看起来对"）；L3 架构（模块边界、依赖检查）；L4 实现（单元、端到端、类型检查、lint，CI 绿灯）；L5 运行时（监控、错误追踪、回滚）。L1、L2 是本质的调节，L3~L5 是派生的调节。

### Claim: Agent 在某方面反复出错时，先问 harness 里有没有一个调节器专门对付这类扰动——没有就加一个，有但不够就增加它的多样性

- **来源**：[[Vibe-Coding系列13：控制论指导Harness-Engineering]]
- **首次出现**：2026-05-07
- **最近更新**：2026-11-24
- **置信度**：0.7
- **状态**：active
- **证据类型**：理论

> 扰动来源包括生成随机性、上下文窗口限制、需求理解偏差、工具调用错误、架构决策歧义、多文件交互副作用，只靠一条系统提示词对付不了。每种机制对付一类扰动：CLAUDE.md 与 rules 对付行为漂移，Spec 对付需求理解偏差，UI 设计稿对付功能对齐漂移，架构约束文档对付结构性退化，单元测试对付单元行为偏差，端到端测试对付用户视角的功能退化，类型系统对付接口约束违反，lint 对付风格漂移，人工评审对付高层目标偏离，记忆与 wiki 对付上下文丢失。这是 [[requisite-variety]] 定律在 harness 上的操作版。

### Claim: 长期项目里不只在调节代码，也在调节调节机制本身——Spec、测试策略、CLAUDE.md、架构约束都要随项目迭代，这是二阶调节

- **来源**：[[Vibe-Coding系列13：控制论指导Harness-Engineering]]
- **首次出现**：2026-05-07
- **最近更新**：2026-11-24
- **置信度**：0.65
- **状态**：active
- **证据类型**：理论

> 一阶控制论问"观察者如何控制系统"（恒温器、PID），二阶控制论承认观察者本身也是系统的一部分。对应到 harness：一阶是人用固定规则约束 agent，二阶是 harness 自己会演化——约束文档每个迭代回顾更新、测试策略按失败模式调整、agent 配置由记忆驱动渐进改进、架构随复杂度重构。结构是"元调节器（人加经验积累）→ 调节机制（harness）→ agent 行为 → 代码、界面、系统"。
