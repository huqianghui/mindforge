# Decision-Policy-Executor Split（决策-策略-执行三分）

## 摘要

把 agent 循环里"下一步做什么"的判断从生成与执行中拆出来，交给一个只返回 typed decision（分布 + confidence）的 [[system-one-model]]；把阈值、兼容性、兜底、绑定、锁、冷却、验收等**所有守边界的逻辑**写成确定性代码；执行（回答、工具调用、UI 动作）仍由 LLM 或执行器完成。三个角色互不越界：判断模型不执行、不授权、不看它不该看的东西；确定性代码不总结或重写执行模型的输入；执行模型不自判"该不该"。

该模式在 vault 内有两个 2026-09-27 的实践：Computer Use 系列八把 Codex 在网页操作里的动作选择交给 Jev（同一执行器只换判断模型的受控对照），Codex Desktop 系列07 在 provider 层用本机网关让 Jev 在七模型 × 四档 effort 间做任务级路由。两文互注"分工同构"。适用前提是：答案空间能在运行时声明成封闭选项、错误成本可由验收器与人工确认兜住、判断的输入可以裁剪成文本/结构化状态。它是 [[generation-evaluation-separation]] 的一种实现形态：生成与门控分离，且门控用不生成文本的模型来做。

## 适用条件

- **前置依赖**：① 决策能表述为 Choice / Score / Noul 三种原语之一；② 有独立于判断模型的验收器（程序化校验字段、`verified_success`、测试结果）；③ 判断输入可裁剪为文本或结构化状态（DOM 元素编号表、近期对话文字、候选组合表），不依赖截图；④ 有一份结果标签或至少 receipt 记录，供后续校准阈值。
- **适用场景**：网页 DOM 可观察、目标明确、有程序化验收、动作可逆的 UI 任务；模型/推理强度路由；意图分类与分支门控；任何"每步都要 LLM 完整思考一次"导致慢且贵的串行循环。
- **不适用场景**：纯视觉、canvas、iframe、需跨站点长流程（判断模型不看截图）；需要多步推理才能判断的复杂决策（单次前向没有测试时算力）；有 stakes 的动作（付款、删除、不可撤销提交）——错误成本主导，任何判断模型都不能替代人工确认；数据边界不允许近期文字发往第三方。

## 步骤

### Step 1: 用规则筛出合法候选集

- **输入**：全部可能动作 / 模型组合；硬约束（用户手选、部署是否存在、effort 是否被支持、不透明历史不迁移、跨 origin 停止）
- **操作**：确定性代码先做筛子——不合法组合在送入判断前就排除；用户点名是最高优先级直接短路
- **输出**：运行时声明的封闭候选集（如 28 个 `模型|effort` 组合 + uncertain；或当前页面元素编号表 + DONE）
- **判断标准**：候选集里每一项都可以被直接执行而不再需要第二次合法性检查

### Step 2: 把判断拆成互相不可见的独立问题

- **输入**：候选集 + 裁剪后的上下文（最新请求单列、近期文字上限 12,000 字符、已知价格字段如实传 null）
- **操作**：一次请求问多个 typed 问题，**把"任务需求是哪一档"与"选哪个型号"拆开**，把"风险有多高"与"是否有能力缺口"作为独立 Noul；明确告知哪些内容不是当前任务（常驻仓库说明）
- **输出**：每个问题一个分布 + 一个 confidence
- **判断标准**：任一问题返回 uncertain 时，其他问题仍能提供兜底依据（"选不准型号"与"任务很难"是两件事）

### Step 3: 确定性策略把判断变成绑定或动作

- **输入**：Step 2 的分布与 confidence；阈值参数；当前绑定状态；冷却与保持时间；缓存成本门槛
- **操作**：confidence ≥ 阈值且不违背明确信号 → 接受；uncertain → 按需求分层兜底而非直接最强模型；高风险 → 走人工确认；超时或非法响应 → 默认组合标 provisional 不重试；已有绑定时只有明确事件（新任务、要求重评、能力缺口证据）才重判；切换算总账（缓存不跨模型）而非比单价
- **输出**：一个可执行的绑定或动作，以及它的来源（Jev 选中 / 分层兜底 / provisional / 用户手选）
- **判断标准**：同一任务内判断次数从"每请求"降到"每任务"；被拒绝的候选不会把它的 effort 拼到当前模型上

### Step 4: 执行并只在必要处调用生成模型

- **输入**：绑定或动作
- **操作**：执行器执行动作 / 网关转发到执行模型；只在需要填写文字时调用 writer；流式转发需 SSE 观察器读取 usage
- **输出**：执行结果 + `receipt.json`（每次 API 调用的模型归属、token、耗时）
- **判断标准**：执行模型的输入、工具定义与 prompt_cache_key 未被网关改写；token 按模型归属记账、不套单一价格

### Step 5: 验收独立于判断，结果标签回流

- **输入**：执行后的页面/任务状态；验收规则（`verify.text_contains`、逐字段比对）；confidence 与实际结果
- **操作**：验收器给出 `verified_success`，不直接接受模型的 `DONE`；把 `prediction · confidence · decision · override · outcome` 记全，供可靠性表反推阈值（见 [[confidence-calibration]]）
- **输出**：任务级记录（成功、耗时分段、费用按模型归属）
- **判断标准**：阈值（如 `min_confidence`、0.7 / 0.7 / 0.2）被标注为"策略值"还是"校准值"；未校准前不宣称正确率

## 决策点

| 条件 | 选择 | 理由 |
|------|------|------|
| confidence ≥ 阈值且不违背明确复杂/高风险信号 | 接受 typed 判断 | 判断层的本职 |
| uncertain + 任务明确 simple + 风险 ≤ 0.2 | 最轻组合（如 luna + low） | "选不准"≠"很难"，按需求分层兜底 |
| uncertain + standard / unknown | 中档默认（如 sol + medium） | 不把不确定等同于最强兜底 |
| 明确 demanding 或风险 ≥ 0.7 | 最强组合 + high | 只有这时才值得最强模型 |
| 已有绑定，要求换模型 | 需能力缺口证据；降档需新任务 + 冷却 + 价格与预测齐全 | 升降级不对称，切换算缓存总账 |
| 价格字段为空 | 禁止纯成本降档、不报告节省 | 缺失字段不补 0 |
| 网页纯视觉 / canvas / iframe / 跨 origin | 交回系统 Browser | 判断模型不看截图 |
| 有 stakes 的动作 | 任一执行器都走人工确认 | 错误成本主导，与判断模型无关 |
| 用户点名执行器或模型 | 服从用户 | 路由规则的最高优先级 |
| 两个判断入口同时存在 | 全机锁，一个运行另一个不能启动 | skill 名字本身不提供互斥，执行器才需要锁 |

## Claims

### Claim: 规则做筛子、typed 判断在筛后的合法候选里选——硬约束留给规则，语义判断交给模型，不是二选一

- **来源**：[[Codex Desktop系列07：用Jev做Auto模型与推理强度路由——七模型与effort的判断设计、与规则匹配和轻量LLM路由的区别、性能准确缓存的平衡]]
- **首次出现**：2026-09-27
- **最近更新**：2026-09-28
- **置信度**：0.75
- **状态**：active

> 规则匹配（关键词/正则/长度/文件类型）六维短板：读不懂上下文（"继续"、"补个测试"看不出改格式还是查并发）、候选空间写死加模型要改代码、输出无把握程度、规则漏写就误判且不知道；优势是零延迟零费用、完全可解释。Jev 反之：近期对话进入判断、候选运行时声明加一行配置、完整分布 + confidence 可设门槛与兜底、低置信度会说"不确定"由代码接管；代价是一次往返 0.2~0.5 秒、无理由文本。所以硬约束（用户手选优先、部署存在、effort 支持、不透明历史不迁移）留给规则，规则筛完 Jev 选。

### Claim: 与轻量 LLM 路由器的八维区别——封闭选项构造上不越界、confidence 是训练目标、单次前向亚秒、输入极低输出免费；代价是无理由、无推理、数据出租户

- **来源**：[[Codex Desktop系列07：用Jev做Auto模型与推理强度路由——七模型与effort的判断设计、与规则匹配和轻量LLM路由的区别、性能准确缓存的平衡]]
- **首次出现**：2026-09-27
- **最近更新**：2026-09-28
- **置信度**：0.7
- **状态**：active

> 轻量 LLM（如 Luna）读上下文输出模型名：生成文本或 JSON 要解析校验、可能输出不在候选里的名字；可以让它写一个置信数但 RLHF 训练的模型没被训练成让这个数与正确率对应；自回归秒级（受控对照里同类单步判断 Astra 2~3 秒）；按输入输出 token 计费；能给理由便于调试；可思维链处理模糊长任务更稳；与执行模型同 Azure 资源数据不出租户；同家族给自家排序可能有偏。Jev：封闭分布不越界、confidence 是 RLCD 训练目标（仍需在自己任务上校准）、0.2~0.5 秒、输入 $0.042/M 输出免费、不给理由、一次前向不做复杂推理、近期文字发往 TypeSafe 需评估数据边界、第三方判别器。两者可叠：Jev 做每次任务开始的快判，仅在返回 uncertain 且任务被判 demanding 时才让 LLM 读更长上下文二次判断——当前实现未做。

### Claim: 把"任务需求"与"型号选择"拆成两个问题是设计里最重要的一步——不确定不再等于最强兜底

- **来源**：[[Codex Desktop系列07：用Jev做Auto模型与推理强度路由——七模型与effort的判断设计、与规则匹配和轻量LLM路由的区别、性能准确缓存的平衡]]
- **首次出现**：2026-09-27
- **最近更新**：2026-09-28
- **置信度**：0.75
- **状态**：active

> 早期版本只问"选哪个模型"，Jev 返回 uncertain 时代码直接用最强模型兜底，一句 "hello, who are you" 也落到 Astra。拆开后"选不准型号"与"任务很难"是两件事：前者按需求（simple/standard/demanding/unknown）分层兜底，后者才需要最强模型。四个问题互相不可见：execution Choice（28 组合 + uncertain，主判断）/ 任务需求 Choice（分层兜底依据）/ 高风险 Noul（只影响选模不授予权限）/ 能力缺口 Noul（已有绑定时是否值得升级的证据）。confidence 是分类的确定程度，不是选中模型的完成率。（已实现、离线 62 项测试通过、归档时共享服务仍是旧版本，"已实现未启用"）

### Claim: 路由粒度是任务不是 input——升降级不对称，Jev 回答的是"当前情况是否值得打破绑定"而非"这条消息属哪一档"

- **来源**：[[Codex Desktop系列07：用Jev做Auto模型与推理强度路由——七模型与effort的判断设计、与规则匹配和轻量LLM路由的区别、性能准确缓存的平衡]]
- **首次出现**：2026-09-27
- **最近更新**：2026-09-28
- **置信度**：0.75
- **状态**：active

> Codex 请求自带 `thread_id` / `turn_id` / `context_window_id`，网关以 thread 为绑定范围、用 turn_id 阻止同回合重复判断；任务可跨多 turn，绑定在任务开始时建立，只有明确事件（新任务、要求重评、能力缺口）才重判。原因是缓存账：缓存不跨模型共享，切换后新模型冷启动；算例——留在 A 读历史 10 万 token 按缓存价 10% 等价 1 万，切到 B 无缓存按普通价（A 的 20%）等价 2 万，B 单价便宜五倍这一次仍贵一倍。所以升级看能力缺口/关键验证反复失败/任务范围扩大，降级等任务结束或明确新任务且价格与预测齐全；最小保持 300 秒、冷却 120 秒、只改 effort 也刷新保持时间否则保持期被绕过。effort 规则：请求里的 `reasoning.effort: low` 无来源标记分不清用户手选还是客户端默认，靠显式策略头 `X-Jev-Effort-Policy: auto|fixed` 传意图并在出站前剥离；max/ultra 不进自动池。已实测：同回合第二次请求读取 15,995 与约 17,400 个缓存 token；Jev 首选 gpt-5.6-terra 下一回合保持、手动 Astra 直通。

### Claim: 事后询问只会更慢，接管循环才是提速来源；单变量受控对照下判断延迟约为 LLM 的 1/8

- **来源**：[[Computer Use与Browser Use系列八：Jev×Codex实践——把动作判断交给System One模型的受控对照、费用账与skill优先级结论]]
- **首次出现**：2026-09-27
- **最近更新**：2026-09-28
- **置信度**：0.75
- **状态**：active

> 探索轮直接拿系统 Browser 与 Jev 执行器比总时间得出"Jev 更慢"，复核发现三处口径不一致（Jev 总时间含关闭临时 Chrome 与守护进程退出约 15.7 s、writer 推理档不同、执行链路与观察方式不同）。修正后只留一个变量：同一本地合成页 1280×720、同一 DOM 观察器与编号规则、同一 Azure gpt-6-astra/medium writer 请求逐字一致、同一系统 Browser 接口 20 步上限 120 s 软截止、逐字段验收——唯一变量是下一步动作由 Astra 还是 jev-1.13.0 判断。结果 8 次正式样本：B1 17.76 s → 6.10 s（−65.7%），B2 23.71 s → 9.84 s（−58.5%）；判断部分 14.62 s → 1.79 s；两组轨迹完全一致（B1 五步、B2 六步）；成功率各 4/4。Jev 组 6 秒分解：6 次判断 29%、1 次 writer 生成用户已给定的 "1000" 占 45%（当前最大可优化项）、开页/观察/动作/验收 26%——判断串行六次是循环结构决定的。数据边界：只有两类简单页面、每组 4 次、无相似选项/动态加载/错误恢复/canvas/iframe/真实站点干扰；不是"完整产品"对照（Codex 原生是一轮批量规划多步，本实验是逐步循环）。

## 实践记录

### Practice: 2026-09-27 — Computer Use 系列八：Jev × Codex 网页动作判断受控对照

- **应用场景**：把 Codex 在网页 UI 操作里"下一步做什么"交给 Jev；封装 `jev-browser` / `jev-desktop` 两个 skill（自动选择、执行前告知、共用凭据加载与 `receipt.json` / `result.json` + 独立 `verified_success`），13 项离线测试覆盖互斥/停止/超时/子进程清理/模型 DONE 后仍需验收
- **实际结果**：部分成功——网页两任务 Jev 组 4/4、耗时 −58~66%、公开价估算费用 −90~96%（B1 $0.0590 → $0.0021，B2 $0.0570 → $0.0055，Jev 组费用几乎全部来自 writer 的 Astra 调用；Jev 组 token 总数是 Astra 组约 1.9 倍但 token 多不等于贵）；桌面 Computer Use 两条路径均阻塞（系统侧 ScreenCaptureKit -3811、Jev Desktop 缺 Accessibility 权限，22.4 s 是启动失败耗时非成绩），无有效数据
- **偏差与调整**：探索轮口径三处不一致导致"Jev 反而更慢"的错误结论，修正为单变量实验；`~/.zshrc` 对非终端进程提前 `return` 导致 key 在 Codex 执行环境不可读，验证方法是在实际执行脚本的进程里检查而非另开终端 export；互斥分层（两 Jev 入口全机锁程序强制 / 与系统工具 `native-begin`/`native-end` 协作式预约 / OS 级不存在不能宣称）
- **经验教训**：结论写成"**条件默认**"而非"优先选择"——数据支持 DOM 型简单网页任务的判断延迟与费用，不支持完整产品对照、桌面场景、一般正确率；`min_confidence: 0.4` 是拍脑袋值未用结果标签校准。升级为"优先选择"还差四个实验：桌面复测、难任务集（相似选项/异步加载/错误恢复/"确实无法完成"，统计错误动作数与错误宣告完成次数）、三臂对照加 Codex 原生批量规划、writer 优化两组同步应用
- **置信度影响**：本页 Claims 置信度 0.7~0.75（实测但样本小、单批次）；[[computer-use]] 页对应 Claims 同水平；四个实验中任两个完成后可上调

### Practice: 2026-09-27 — Codex Desktop 系列07：Auto / Jev 七模型与 effort 路由网关

- **应用场景**：在 Codex 模型菜单加 `auto-jev` 目录别名，本机回环网关（约 1,800 行标准库 Python：gateway / jev / policy / effort / install / control，SQLite 状态，launchd 生命周期）调 Jev 在七个 Azure 部署 × 四档自动 effort 的 28 个合法组合间做任务级绑定；与 CodexSaver 的区别是 provider 层透明路由，Codex 本身不知道后面换了谁
- **实际结果**：部分成功——已实测：真实链路（Jev 首选 gpt-5.6-terra、下一回合保持、手动 Astra 直通）、同回合两次请求只调一次 Jev、七模型工具矩阵全部通过（逐个指定后端）、CLI `-m auto-jev` 走正式配置、Desktop 菜单可见；已实现未启用：任务分层兜底与 provisional、(模型, effort) 联合选择与 auto/fixed 策略头（离线 62 项测试通过，归档时共享服务仍是旧版本）；待校准：阈值 0.7/0.7/0.2 与三档兜底的分类质量与真实延迟、Azure 实际费率、28 组合质量费用对比
- **偏差与调整**：Desktop 菜单选择后回退的原因是项目级 config 固定了模型覆盖全局（已移除）；v1→v2 修正"uncertain 直接最强兜底"为拆开任务需求与型号选择；v3 把决策对象扩成 (模型, effort) 联合 Choice；安装器先起服务再改配置并哈希校验回滚
- **经验教训**：价格字段全为 null 时**如实传 null 而非猜**，并禁止纯成本降档、全文不报告节省金额——路由的收益不是"选到便宜模型"而是在性能/准确率/缓存命中/费用四量间找可运行平衡点；文章严格区分已实测 / 已实现未启用 / 待校准三类事实
- **置信度影响**：已实测项 0.8，已实现未启用 0.6，策略阈值 0.5；[[model-routing]] 与 [[prefix-caching]] 页对应 Claims 按此分级

## 关联概念

- [[system-one-model]] — `implements` 该模式是 System One 模型在 agent 循环里的接入方式：judge 用 typed decision，边界用确定性代码
- [[confidence-calibration]] — `uses` 阈值与兜底依赖 confidence；未做应用层校准前阈值只能标为"策略值"
- [[generation-evaluation-separation]] — `implements` 生成与门控分离的一种实现：判断层不生成、执行层不自判、验收独立于两者
- [[cost-per-task]] — `uses` 费用按模型归属记账、切换算缓存总账、价格为空不报节省——任务完成花费口径在路由与执行器层的落地
- [[model-routing]] — `extends` 在"昂贵模型判断、廉价模型执行"之上加了第三个角色：判断本身也可以交给不生成文本的决策模型，并把粒度从每请求提到每任务
- [[computer-use]] — `addresses` 解决 GUI action loop 里"每步都让 LLM 完整思考一次"导致的串行慢与贵；不解决纯视觉与桌面权限问题
- [[prefix-caching]] — `uses` 任务级绑定与最小保持时间的依据是缓存不跨模型共享，切换要算总账

## 关联方法
